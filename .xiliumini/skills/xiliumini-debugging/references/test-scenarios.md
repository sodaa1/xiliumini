# 测试场景（Test Scenarios）

本文件用于验证 xiliumini-debugging 技能是否按四阶段工作流正确执行。四阶段固定为 Investigation → Pattern Comparison → Hypothesis Testing → Fix & Verify。对每个场景，先说明期望运行的阶段与每阶段产出，再给出可供评分者检查的**可检验断言**（断言应能客观核对“有/无”或“是/否”，不依赖主观判断）。

按需加载：仅在需要设计或评审测试用例时读取本文件，不要默认塞进主上下文。

---

## 场景 A：确定性异常（deterministic exception）

**输入示例**：`config.get("retry")` 在某个已知配置下必然抛出 `KeyError`，100% 复现；用户说“跑一下这个脚本就报错”。

**期望阶段行为**

- Investigation（必做）：完整读取 `KeyError` 的 stack trace，定位抛错帧与调用链；给出最小复现命令并确认为 100% 复现；检查最近变更（`git log`/`git diff`）；指出错误是在哪个边界/层级（如配置读取层）引入的。产出：复现步骤 + 抛错的第一个错误假设位置。
- Pattern Comparison（必做）：在同仓库找一个“能正常工作”的相似配置读取实现作对照，列出关键差异（键名、默认值、初始化顺序）与依赖假设。产出：对照基线与差异清单。
- Hypothesis Testing（必做）：提出单一可证伪假设，例如“根因是配置键名不一致导致 `KeyError`”，用最小实验（打印实际键集合）验证。产出：假设 + 验证结果。
- Fix & Verify（必做）：先写能稳定触发 `KeyError` 的失败测试（Red），再做最小根因修复（Green），运行相关测试并报告剩余风险。产出：Red→Green 证据 + 回归结果。

**可检验断言**

1. 报告中根因陈述唯一且与 stack trace 指向的抛错位置一致，未出现未调查就直接改动的痕迹。
2. 复现步骤可被独立执行并稳定复现该异常（复现率标注为 100%，如 10/10）。
3. 存在修复前失败、修复后通过的同一测试（Red→Green 对应关系明确）。
4. Pattern Comparison 阶段至少引用一个同仓库可工作的相似实现及其关键差异。

## 场景 B：pytest 回归（previously-passing test now fails）

**输入示例**：昨天通过的 `tests/test_pricing.py::test_discount` 现在失败，用户说“这个测试昨天还是绿的，现在挂了”。

**期望阶段行为**

- Investigation（必做）：完整读取 pytest 失败输出与断言差异（期望值 vs 实际值）；建立单测级最小复现命令（如 `python -m pytest tests/test_pricing.py::test_discount -q`）；用 `git log`/`git diff` 定位最近变更，判断是业务代码还是测试/夹具改动引入。产出：复现命令 + 变更时间线。
- Pattern Comparison（必做）：找同文件或同目录中仍通过的相关测试作为对照，比较夹具、数据与依赖假设的差异。产出：对照测试与差异点。
- Hypothesis Testing（必做）：一次一个可证伪假设（如“最近改动的取整逻辑导致期望值不匹配”），用最小实验或临时改动验证。产出：假设与实验结论。
- Fix & Verify（必做）：保证存在可稳定复现原失败的测试（Red），做最小根因修复（Green），运行该测试及相邻回归测试套件并报告结果。产出：Red→Green + 回归套件输出。

**可检验断言**

1. 明确运行了至少一条针对该测试的最小复现命令，并记录其失败输出。
2. 通过最近变更（git 历史/差异）给出回归的时间或提交定位，而非仅凭猜测。
3. 修复后同一测试由失败转为通过，并额外运行了相邻回归测试且结果被报告。
4. 剩余风险章节说明了未覆盖的相邻场景或对下游的潜在影响。

## 场景 C：不可复现的间歇性故障（flaky / intermittent failure）

**输入示例**：一个异步任务的集成测试偶尔超时或顺序错乱，本地约 1/20 概率失败，用户说“有时候会挂，重跑又过了”。

**期望阶段行为**

- Investigation（必做）：收集失败样本与日志、堆栈（若有多例则对比共同点）；记录真实复现率与触发条件；识别竞态/超时所在边界（线程、协程、外部服务、共享状态）；检查最近变更。产出：失败样本 + 复现率 + 嫌疑边界。
- Pattern Comparison（视情况）：若仓库中有稳定的相似异步实现，则对照其同步/等待方式与依赖假设；若没有可比对象，应明确说明并跳过，而不是编造对照。产出：对照或“无可比实现”的说明。
- Hypothesis Testing（必做，且强调单一假设）：一次只提出一个可证伪的竞态假设，用确定性手段验证（注入延迟、放大并发、加事件埋点、固定随机种子/时钟），而不是靠“多跑几次看看”。若证据不足必须明确声明“当前证据不足以定位”，不得用多个随意改动代替调查。产出：假设 + 可重复的验证手段与结论。
- Fix & Verify（必做）：用能稳定刺激竞态的失败测试（Red，可通过受控延迟或确定性调度实现），做最小根因修复（Green，例如改为等待实际条件而非 `sleep`），并运行相关与回归测试，说明为何不再依赖时序碰运气。产出：Red→Green + 稳定性证据 + 剩余风险。

**可检验断言**

1. 明确记录故障的复现率或失败样本数量，且承认并区分“尚未稳定复现”的状态。
2. Hypothesis Testing 阶段同一时间只存在一个被验证的根因假设，未出现多个并发随意改动。
3. 修复方案使用“等待实际条件”（事件/条件变量/轮询就绪）等确定性机制，而非新增硬编码 `sleep` 掩盖竞态。
4. 若证据不足，报告显式声明证据缺口与下一步所需证据，而不是给出未经证实的根因结论。

---

## 通过标准小结

- 三个场景都必须覆盖 Investigation 与 Fix & Verify；Pattern Comparison 在场景 C 允许在无可比实现时明确跳过。
- 每个场景的断言均为可客观核对的“有/无”“是/否”判断，评分者无需主观评价即可判定通过与否。
- 任何场景若出现“未调查就直接改”“以多个随意改动代替调查”“用硬编码 `sleep` 掩盖竞态”，即判定不符合技能要求。
