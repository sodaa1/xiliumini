# xiliumini 调试流程

当任务是 Python bug、测试失败、行为异常或构建/集成问题时，用本流程把"猜"替换成"证据 + 可复现实验"。目标是找到并修复根因，而不是让错误暂时消失。

## 何时适用

适用：用户要求 debug / 排查 / 修复报错；pytest 或其他测试失败；配置异常；构建、依赖、集成故障；难以复现的间歇性问题。

不适用：纯概念答疑、API 用法讲解、代码评审请求（无具体故障）——直接回答即可，不要启动本流程。

## 强制四阶段工作流

按顺序执行，不要跳步。每阶段产出都要能被他人复核。

### 1. Investigation（调查）

先理解，再动手。禁止在未调查的情况下直接修改代码。

- 完整读取错误信息与 stack trace：从最后一行 `Error`/`Exception` 向上读到最早的业务代码帧，不要只看被截断的头部。
- 建立可复现步骤：写出最小的触发命令与输入，记录是否 100% 复现。
- 检查最近变更：`git log`、`git diff`、依赖版本变化、配置变更，把"什么时候开始坏的"与代码历史对齐。
- 多组件问题时先定位边界：确认错误是在哪个边界被引入的（进程间、模块间、序列化层、网络层、DB/API 边界），而不是先猜测。
- 沿调用链向上追踪：从抛错点往回走到调用者，直到找到第一个做出错误假设的位置——那才是根因所在层级。

### 2. Pattern Comparison（模式对比）

在同仓库里找一个"能正常工作"的相似实现，作为对照基线。

- 对齐关键差异：签名、参数顺序、默认值、异常处理、初始化顺序、生命周期。
- 显式列出依赖假设：环境变量、版本、路径、并发模型、外部服务可用性。
- 差异点往往就是嫌疑点；把它变成阶段 3 的候选假设，而不是立刻改代码。

### 3. Hypothesis Testing（假设验证）

一次只提出一个可证伪的根因假设。

- 把假设写成"如果 X 是根因，那么做 Y 会出现 Z"的可验证形式。
- 用最小化实验验证：加日志、写一次性最小脚本、缩小输入、二分定位（`git bisect` 或注释掉一半逻辑）。
- 证据不足时明确说明"当前证据不足以定位根因"，并说明还缺什么证据，而不是用多个随意改动去碰运气。
- 禁止用一堆同时改动代替调查：那会破坏因果可归因性。

### 4. Fix & Verify（修复与验证）

先 Red，后 Green。

- 先建立失败测试（Red）：写一个能稳定复现该 bug 的测试，确认它在修复前失败。
- 再做最小根因修复（Green）：只改根因所需的最小范围，不做顺手的无关重构。
- 运行相关测试与回归测试，报告实际结果（命令 + 输出摘要）。
- 明确列出剩余风险与未覆盖场景。

## 守则（Guards）

- 禁止未调查就直接改代码。
- 连续三次修复尝试失败，应停止继续叠补丁，退回阶段 1 重新审视架构与假设。
- 异步/偶发问题优先"等待实际条件"（事件、future、就绪探针、条件变量），不要用硬编码 `sleep` 掩盖竞态。
- 在入口、业务逻辑、环境三层做适当校验：入口做输入/类型校验，业务层做不变量与状态校验，环境层校验依赖版本、配置与外部服务可用性。
- 文件写入、命令执行、网络查询只能使用 xiliumini 已授权的 Tool，且必须经过 Tool Policy。本技能不能自行授予权限，不能要求绕过审批，不得默认安装依赖或执行未受信任脚本；需要新权限时，向用户说明并走正式授权流程。

## 调试报告模板

每个调试任务结束时，用固定模板汇报，章节顺序不可变：

```markdown
## Symptoms
（观察到的现象：错误信息、失败测试、异常行为，含时间/频率）

## Reproduction
（最小复现步骤与命令；复现率；所需环境）

## Evidence
（证据清单：stack trace 关键帧、日志片段、git 历史、对比实现的差异、实验输出）

## Root cause
（一句话根因 + 支撑它的具体证据；指出引入错误的边界/层级）

## Hypothesis
（被验证的假设及其可证伪形式；验证方式与结果）

## Minimal fix
（改动文件与最小改动说明；为什么不影响其他行为）

## Tests
（新增/运行的测试命令与结果：Red → Green → 回归）

## Remaining risks
（剩余风险、未覆盖场景、后续跟进项）
```
